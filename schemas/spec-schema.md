# SPEC Schema Documentation

**JSON Schema:** [`spec.schema.json`](./spec.schema.json)
**Version:** 1

## Overview

This schema defines the machine-readable contract for SPEC.md files generated by the Shikamaru Speccer.

## Required Sections

| Section | Type | Description |
|---------|------|-------------|
| `schemaVersion` | integer | Must be `1` |
| `project` | string | Project name |
| `overview` | object | Objective and deliverable |
| `stack` | object | Technical stack |
| `architecture` | object | Project structure |

## Section Details

### overview (required)

| Field | Required | Description |
|-------|----------|-------------|
| `objective` | Yes | Project objective (min 20 chars) |
| `deliverable` | Yes | What the client receives |
| `users` | No | Target users (target, count, profile) |

### stack (required)

| Field | Required | Description |
|-------|----------|-------------|
| `language` | Yes | Language with name, version, justification |
| `framework` | Yes | Framework with name, version, justification |
| `database` | No | Database choice |
| `hosting` | No | Hosting platform |
| `dependencies` | No | Key dependencies array |

### architecture (required)

| Field | Required | Description |
|-------|----------|-------------|
| `structure` | Yes | Directory structure array (path + description) |
| `patterns` | No | Applied design patterns |

### conventions (optional)

| Field | Description |
|-------|-------------|
| `rules` | Project-specific rules |
| `antiPatterns` | What NOT to do |

### Optional Sections

- `features` - List of features with status
- `dataModel` - Entities and relations
- `integrations` - External API integrations
- `errorHandling` - Error strategies
- `edgeCases` - Edge cases and handling
- `deployment` - CI/CD, env vars, domain
- `constraints` - Budget, deadline, legal
- `successMetrics` - Project KPIs
- `uxui` - UI/UX specifications (if applicable)
- `testing` - Test strategy (level, framework, coverage)
- `marketing` - SEO, analytics (if applicable)
- `research` - Technical research results

## Integration Details

Each integration in `integrations` array can have:

| Field | Required | Description |
|-------|----------|-------------|
| `name` | Yes | Service name |
| `usage` | Yes | What it's used for |
| `baseUrl` | No | API base URL |
| `auth` | No | Auth method |
| `endpoints` | No | Used endpoints |
| `rateLimit` | No | Rate limits |
| `envVar` | No | Environment variable |
| `gotchas` | No | Known issues |

## Example

```json
{
  "schemaVersion": 1,
  "project": "my-project",
  "status": "VALIDATED",
  "overview": {
    "objective": "Build a B2B lead enrichment pipeline",
    "deliverable": "Python CLI + API endpoint"
  },
  "stack": {
    "language": { "name": "Python", "version": "3.12", "justification": "Team expertise" },
    "framework": { "name": "FastAPI", "justification": "Fast, async, typed" }
  },
  "architecture": {
    "structure": [
      { "path": "src/", "description": "Main source code" },
      { "path": "tests/", "description": "Test files" }
    ]
  },
  "successMetrics": [
    { "metric": "API latency p95", "target": "< 200ms" },
    { "metric": "Data quality", "target": ">= 90% accuracy" }
  ]
}
```
